
===== PAGE 1 =====

Student Attendance — Final End-to-End Blueprint
Commercial Android APK + free web launch + PC dashboard + Flask API + PostgreSQL. Designed for direct APK distribution
without Play Store.
1. Final Product Goal
Commercial Student Attendance product for schools, colleges and training institutions.
Primary mechanism: teacher generates a short-lived 6-digit attendance code; students enter that code in the Android app.
Distribution: Android APK downloaded directly from your free web launch page. No Play Store is required.
PC use: institution administrators and teachers can use the web dashboard. The core student experience remains mobile.
Recommended V1 target: Android first. iOS can be added later.
2. Zero/Low-Cost Launch Architecture
Launch page: Vercel Hobby plan or another free static hosting option, using a free provider URL such as a Vercel subdomain
initially.
Source control: GitHub Free.
APK: signed release APK linked from the launch page.
Backend: Flask REST API on a free/low-cost backend service that supports Python web applications. Choose the provider at
deployment time based on current free-tier limits.
Database: PostgreSQL on a free/low-cost managed PostgreSQL provider where available.
Important: free tiers can change or sleep. For a real paying institution, move the API/database to paid production infrastructure
before promising SLA-level reliability.
Do not store passwords, secrets or the production database in the website repository.
3. System Architecture
Student Android App → HTTPS → Flask REST API → PostgreSQL.
Teacher Android App for attendance session creation → same Student product API → PostgreSQL.
PC Admin/Teacher Dashboard → HTTPS → Flask REST API → PostgreSQL.
Vercel hosts the public launch/download page and can host a separate admin web frontend. It is not the database.

10. Attendance Session Algorithm
Teacher selects class + section + subject.
Backend creates a session using server time.
Backend generates a cryptographically random 6-digit code.
Code expires/rotates after approximately 30–60 seconds.
Student sends authenticated request containing the code and session information.
Backend validates institution, class/section membership, session state, code and time window.
Backend checks duplicate attendance using both application logic and a database uniqueness constraint.
Backend assigns PRESENT or LATE according to institution policy.
Backend records timestamp using server time.

Teacher sees live count and can close the session.

11. Suggested Timing Policy
Example only: class start 9:00 AM; 9:00–9:10 PRESENT; 9:10–9:20 LATE; after cutoff student self-check-in closes.
All timing values should be configurable by institution.
Server time is authoritative; never trust the student's device clock.
12. Anti-Proxy Controls
Authenticated student account.
Correct institution/class/section.
Active attendance session.
Short-lived random code.
Server timestamp.
Duplicate prevention.
Rate limiting on code attempts.
Optional check-in proximity/location later.
Audit trail for corrections.
Do not advertise the system as fraud-proof.
